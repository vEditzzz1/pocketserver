            One site, four layers
            
      
              
        
            1. Panel on :9090 — a server inside the app, driving the same engine as the dashboard.
              2. 
        
            2. Runtime mode — decides who runs a guest command: PRoot, chroot, Shizuku or the VM.
              3. 
        
            3. Distro — the filesystem that command lands in: Alpine 3.24 or Ubuntu 24.04.
              4. 
        
            4. Site — a process inside that guest, listening on its port (8080 for www).
              5. 
      
            
      
            When a mode and a distro cannot be the same guest — Ubuntu inside the Alpine VM — the app refuses and says why instead of pretending it worked.
            
    
            

    
            
      
            Runtime modes
            
      
            Change it on System. The mode decides how a command enters Linux; it does not change which distro you are in.
            

      
            
        PRoot · app UID default
        
            A fake root. proot runs as the app's own UID and rewrites paths, so a full userland works on a phone with no root at all.
            
        
            
          
            When selected
            Every guest command — site starts, package sets, probes — runs through proot as the app UID.
            
          
            Needs
            Nothing. This is the mode that always works.
            
          
            Gives
            Alpine or Ubuntu, apk/apt package sets, container sites, the panel.
            
          
            Limits
            No real root; ports under 1024 cannot be bound; sites stop when the app process is killed.
            
        
            
      
            

      
            
        Root · chroot
        
            A real chroot through su (Magisk), with /proc, /dev and /sys mounted and volumes bind-mounted.
            
        
            
          
            When selected
            Guest commands run as real root inside a real chroot on your selected distro.
            
          
            Needs
            Root granted to the app.
            
          
            Gives
            Everything PRoot gives, plus real UIDs and privileged ports (80, 443).
            
          
            Limits
            Needs root; a broken root setup fails every site; the app cannot start a command it has no root for.
            
        
            
      
            

      
            
        Shizuku · shell
        
            The same PRoot runtime, but started by the Shizuku service instead of by the app, so sites keep serving after the app is closed.
            
        
            
          
            When selected
            Commands are launched through Shizuku and keep running with the app out of the picture.
            
          
            Needs
            Shizuku running and permission granted.
            
          
            Gives
            Alpine or Ubuntu, package sets, container sites, and sites that outlive the app.
            
          
            Limits
            No privileged ports unless the Shizuku server itself runs as root — then the guest gets real root too; if Shizuku stops, new commands fail.
            
        
            
      
            

      
            
        Podroid · VM
        
            A real Alpine kernel (Podroid's UML engine) with its own 2 GB overlay, started outside the app sandbox through Shizuku. 768 MB RAM, 2 CPUs.
            
        
            
          
            When selected
            Site commands run inside the guest over the TCP bridge on 9099. While the VM is up it owns every forwarded port, so the app routes commands into it even if another mode is selected.
            
          
            Needs
            Shizuku, plus the VM images (306 MB, one-time download).
            
          
            Gives
            A genuine kernel and root inside the guest; sites survive the app being killed.
            
          
            Limits
            Alpine only — it cannot be Ubuntu; container sites do not work in it (their rootfs is not entered); the host port is forwarded by QEMU as the app UID, so still no ports under 1024.
            
        
            
      
            
    
            

    
            
      
            Distros
            
      
            Change it on System. Switching stops every site and the Podroid VM, then points the runtime at the other filesystem.
            

      
            
        Alpine 3.24
        
            
          
            What it is
            The userland bundled in the APK (~237 MB installed), package manager apk.
            
          
            When selected
            PRoot, Root and Shizuku enter this filesystem; package sets install with apk. It is also the guest the Podroid VM runs.
            
          
            Best for
            Everything, and the only distro that can be used together with the Podroid VM.
            
        
            
      
            

      
            
        Ubuntu 24.04
        
            
          
            What it is
            A one-time 28 MB download from cdimage.ubuntu.com, ~105 MB on disk, apt with noble, noble-updates and noble-security on ports.ubuntu.com.
            
          
            When selected
            PRoot, Root and Shizuku enter Ubuntu; package sets install with apt (busybox-static, python3, nginx, nodejs…). The filesystem is separate from Alpine, so packages installed there do not exist here.
            
          
            Best for
            Software that expects Debian/Ubuntu — and it cannot be used together with the Podroid VM.

            What does not work
            
      
              
        
            • Ubuntu inside the Podroid VM. The guest image is Alpine, so the VM refuses to boot while Ubuntu is selected; with Podroid mode chosen, sites fall back to PRoot and say so.
              • 
        
            • Container sites while the VM is on. The VM runs the command in the guest instead of entering the image's own filesystem, so containers belong to the other three modes.
              • 
        
            • Two runtimes on one port. A port can only be held by one process: while the VM forwards 8080, a PRoot site on 8080 cannot bind. The app forwards a running site's port when the VM starts, and takes it back when the VM stops, but never shares it.
              • 
        
            • Ports under 1024 without privileges. PRoot runs as the app UID and cannot bind them; Root mode always can, and Shizuku can when its own server runs as root.
              • 
        
            • Container isolation. No PID or IPC namespaces, no cgroups, no port publishing, no read-only volumes: a container is a filesystem, not a sandbox.
              • 
        
            • Running with the app frozen. If the OS suspends the app (the Power row can exempt it), the panel stops answering even though the guest keeps running.
